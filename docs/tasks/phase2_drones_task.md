## Контекст

Репозиторій уже містить фазу 1 (`src/airalert/`): Telethon-клієнт, незмінний журнал `raw_messages` у SQLite, ідемпотентний backfill, live-колектор, `alerts.parquet`. **Перевикористовуй цю інфраструктуру, не пиши паралельну.**

Що ми вже знаємо (перевір у себе, не приймай на віру):
- З ~17.08.2026 Київ у новому режимі: тривог ~2.4× більше, переважно реактивні «шахеди» (~600 км/год ≈ 10 км/хв) поодинці або малими групами, цілодобово. Тому **історію беремо лише з 2026-08-10** (тиждень запасу до зламу). Старіша історія — інший режим.
- Офіційний канал `air_alert_ua` мертвий з 07.09; для тривог живе лише `UkraineAlarmSignal`.
- Горизонт прогнозу всього проєкту: **до 120 хв**.
- Просторовий сигнал реальний, але короткий: районні тривоги Київщини дають лифт ~9× на 15 хв, ~3× на 30 хв, ~1.7× на 60 хв. Треки мають покращити саме перші 30–60 хв.
- У повідомленнях **немає ідентифікаторів дронів**. Є лише «в області X ... курсом на населений пункт Y», іноді з кількістю. Треки доведеться збирати самим (псевдо-треки).

Формат `@kudy_letyt` (з превʼю, **перевір на справжній історії**):
```
Київщина:
Реактивний БпЛА курсом на Бровари
2х Реактивні БпЛА курсом на Васильків
Чернігівщина:
3х.Реактивні БпЛА курсом на Славутич
```
`@kyiv_nebo` — вільний текст про райони/масиви Києва без напрямку («Троєщина», «Святошин, Нивки», «Сам Київ поки без загроз»).

## Мета

1. Зібрати історію (з 2026-08-10) і живий потік з каналів моніторингу.
2. Без LLM розібрати повідомлення на структуровані згадки: тип цілі, кількість, область, ціль курсу → координати.
3. Склеїти згадки в псевдо-треки і побудувати **ймовірнісну модель руху** (корельоване випадкове блукання / Монте-Карло), відкалібровану на історії.
4. Видати as-of фічі на 5-хв сітці для моделі тривог: «поле тиску» на Київ на горизонтах 15/30/60/120 хв.
5. Окремий маленький колектор SITREP alerts.in.ua (районний стан Київщини, жовтий/червоний рівень).
6. Зручний `docker-compose` для перенесення готових модулів з Mac на сервер.

**Не входить**: модель тривог, симулятор, API, фронтенд.

## B. Парсер без LLM

Модуль `src/airalert/drones/` з чистими функціями.

**1. Нормалізація**: NFC, апострофи `'’ʼ` → `'`, прибрати емодзі/форматування, розбити на рядки.

**2. Класифікація повідомлення** (правила + словник ключів; TF-IDF/логрег — лише якщо правил забракне): `drone_jet`, `drone`, `missile`, `ballistic`, `kab`, `all_clear`, `explosions`, `other`.

**3. Розбір рядків** — стан-машина: рядок-заголовок області (`Київщина:`, `Кіровоградська:`, `Київ:`) задає поточну область; рядки-цілі:
```
(?P<count>\d+)\s*[хx]\.?\s*   (опційно)
(?P<kind>Реактивн\w*|БпЛА|Шахед\w*|...)
.*?(?P<rel>курсом на|у напрямку|в напрямку|в районі|над|з боку)\s+(?P<place>.+)$
```
Регекси — у таблиці шаблонів з тестами, не розкидані по коду.

**4. Газетир**: GeoNames `UA.zip` (feature class P + admin1 для області) + ручний список ~60 районів/масивів/станцій Києва з координатами (`data/gazetteer/kyiv_local.csv`: Троєщина, Дарниця, Жуляни, Позняки, Виноградар, Святошин, Нивки, Відрадний, ...). Обидва в репозиторії (GeoNames CC-BY — атрибуція в `LICENSES/`).
- Відмінки: «на Дарницю» → «Дарниця», «на Бровари» → «Бровари». Спершу pymorphy3 (`pymorphy3-dicts-uk`), fallback — таблиця суфіксних правил, далі точний збіг, далі fuzzy (rapidfuzz ≥ 92) **лише в межах області з заголовка**.
- Тезки (Олександрівка, Березанка, ...) розрізняються областю із заголовка; якщо області нема і кандидатів > 1 — `ambiguous`, координат не ставимо.
- Усе, що не знайдено → `parse_misses`; у звіті топ-50 нерозпізнаних назв (я доповню словник вручну).

**Вихід** — таблиця `drone_mentions`:
`channel, msg_id, line_no, posted_at, known_at, oblast, kind, count, rel, place_raw, place_norm, lat, lon, match ∈ {exact,lemma,fuzzy,ambiguous,none}, dist_to_kyiv_km, bearing_to_kyiv_deg`.

**5. Валідація з Claude як розмітником.** Команда `airalert drones-sample --n 300` — стратифікована вибірка рядків (по каналах, типах, match) у `data/labels/sample.jsonl` (поля: id, текст повідомлення, рядок). Я розмічу її в чаті з Claude і поверну `data/labels/gold.jsonl`. Команда `airalert drones-eval` рахує точність/повноту для `kind`, `count`, `oblast`, `place_norm`. **Ціль: place ≥ 90% precision, ≥ 85% recall на kudy_letyt.** Нижче — зупинись і покажи помилки.

## C. Псевдо-треки і модель руху (прогноз напрямку)

**1. Асоціація згадок у треки** (`tracker.py`): згадка j продовжує трек i, якщо
`posted_j − posted_i ≤ 20 хв`, той самий клас швидкості, і відстань від цілі i до цілі j ≤ `v_max(kind) × Δt + 30 км`. Жадібно, найближчий кандидат; кількість («2х») переноситься. Трек закривається після 25 хв без продовжень. Стан треку: остання оцінка позиції (ціль попередньої згадки, або центроїд області, якщо попередньої нема), курс (бік на ціль поточної згадки), клас швидкості.
Це наближення — задокументуй його і виміряй частку згадок, що потрапили в треки довжини ≥ 2.

**2. Модель руху** (`motion.py`) — корельоване випадкове блукання (це і є «броунівський рух» для курсу):
- курс: `θ_{k+1} = θ_k + σ_θ·√Δt·ε`, ε ~ N(0,1);
- швидкість: lognormal навколо класу (`jet` ≈ 10 км/хв, `drone` ≈ 3 км/хв), розкид σ_v;
- Монте-Карло, 2000 частинок на трек, крок 1 хв, до 120 хв.
- Вихід на трек: `P(вхід у коло R=20 км навколо центру Києва до t+H)` для H ∈ {15, 30, 60, 120} і розподіл часу прибуття.

**3. Калібрування на історії** (без витоку: параметри підбираються лише на періоді до валідації):
- для кожної пари сусідніх згадок треку: передбачений розподіл позиції через Δt vs фактична ціль наступної згадки → лог-правдоподібність;
- grid/MLE по `σ_θ`, `σ_v`;
- **бейзлайни**: (a) пряма лінія з постійною швидкістю без шуму, (b) «залишається на місці». Модель руху має бути не гіршою за (a) за лог-правдоподібністю, інакше чесно фіксуємо, що шум не допомагає.
- Звіт `reports/drone_motion.md`: параметри, лог-правдоподібність vs бейзлайни, hit-rate «справжня наступна ціль у 50% / 80% регіоні прогнозу», 5 прикладів треків на карті (статичні PNG).

Спліти часу: калібрування `2026-08-10 … 2026-09-12`, перевірка `2026-09-13 … 2026-10-11` (той самий тестовий період, що й у моделі тривог).

## D. Фічі «поле тиску» для моделі тривог

`airalert drones-features` → `data/processed/drone_features.parquet`, 5-хв сітка UTC, **as-of**: у рядку для моменту t лише згадки з `known_at ≤ t`.

Фічі (усі з треків, активних на момент t):
- `n_tracks_r{30,80,150,300}` — кількість активних треків у кільцях від Києва (з урахуванням `count`);
- `n_heading_kyiv` — треки, курс яких у межах ±30° від напрямку на Київ;
- `n_target_kyiv_ring` — згадки «курсом на» населені пункти в радіусі 30 км (Київ, Бровари, Бориспіль, Васильків, Гостомель, Ірпінь, ...);
- `min_eta_min` — мінімальний медіанний час прибуття (NaN, якщо нема);
- `p_any_reach_{15,30,60,120}` = `1 − Π(1 − p_i)` по треках (з моделі руху);
- `n_jet_active`, `mentions_last_{15,60}m`, `minutes_since_last_kyiv_ring_mention`;
- `kyiv_nebo_over_city` — чи був пост `kyiv_nebo` з районом Києва за останні 10 хв.

**Тест без витоку обовʼязковий**: для випадкових t перебудувати фічі з даних, обрізаних по t, і порівняти з фічами з повного прогону — мають збігатися побітово.

Швидка перевірка корисності (у звіт, без моделювання): лифт `P(тривога в Києві почнеться за H | фіча > 0)` vs `| фіча = 0` для H = 15/30/60/120 на період калібрування. Порівняти з лифтом районних тривог (≈9 / 3 / 1.7). Якщо треки не дають більше — скажи прямо.

## F. Docker Compose (Mac → сервер)

Вимоги:
- Один `docker-compose.yml` + `.env` на кожному хості (`.env.example` в репо). Профілі:
  - `collect` — `tg-collector` (тривоги + дрони, одна сесія), `sitrep-collector`;
  - `process` — `features-worker` (раз на 30–60 с перераховує поточні фічі дронів у `data/live/state.json`), `nightly` (rebuild + recalibration о 04:00);
  - `serve` — місце під `api`/`web` (заглушки, без відкритих портів поки).
- Образ один (multi-stage, `uv sync --frozen`), різні `command`. **Збірка на цільовому хості** (Mac arm64 / сервер amd64) — без закріпленої платформи; або `docker buildx` multi-arch — на твій вибір, задокументуй.
- Безпека: non-root, `read_only: true` + `tmpfs: /tmp`, `cap_drop: [ALL]`, `security_opt: no-new-privileges`, жодних `ports` (майбутній api — лише `127.0.0.1:8000`), сесія Telethon як bind-mount з правами 600 поза репо, `env_file: .env`.
- `restart: unless-stopped`, healthcheck через heartbeat у SQLite (≤ 5 хв), логи з ротацією (`max-size: 10m`, `max-file: 3`).
- Томи: `./data/live` (стан), `./data/processed` (результати); зміни коду не вимагають перезапису даних.
- `Makefile`: `make up-collect`, `make up-all`, `make logs`, `make backfill`, `make features`, `make test`, `make deploy HOST=...` (rsync коду + `docker compose up -d --build` на сервері; дані не rsync-ити).
- README-розділ «Розгортання»: що копіювати на сервер вручну (`.env`, файл сесії), як перевірити здоровʼя.

## Тести (pytest, офлайн)

- Парсер на ≥ 40 реальних фікстурах з `kudy_letyt` (+ 10 з `kyiv_nebo`, `kpszsu`): заголовки, `2х`/`3х.`, кілька областей в одному пості, відмінки, тезки, порожні/рекламні пости.
- Газетир: відмінки → називний; тезка без області → `ambiguous`.
- Трекер: синтетичні послідовності (продовження, розрив > 25 хв, неможлива швидкість → новий трек).
- Модель руху: при `σ_θ = 0, σ_v = 0` збігається з аналітичною прямою; `p_reach` монотонно не спадає з H; відтворюваність при фіксованому seed.
- Фічі: тест без витоку (див. D).
- Compose: `docker compose config` валідний; smoke `collect` профілю з фейковим клієнтом.
